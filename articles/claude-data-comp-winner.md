「特徴量名が全部マスキングされてるって、どうしろって話ですよ」

研修の最終課題、機械学習コンペが始まった朝。隣の席の同期がそうこぼした。100種類超の特徴量がすべて`feature_001`形式。目的変数は時系列で変化する数値。評価指標はRMSE。使えた時間は半日。同期のその一言を聞きながら、自分は別のことを考えていた——このデータ、うちの工場で何度も見てきたパターンに似ている、と。

半日後、同期20人中1位をとった。コードはClaudeがほぼ書いた。自分がやったのは、現場感覚から来た3つの判断だけだ。それでも結果を分けたのは、その3つだった。

**対象読者：** 製造現場のデータを日常的に触っているが、機械学習は専門家のものと思っているエンジニア。AIツールを使い始めたが、どこまで任せてよいか分からない人。

---

## このデータ、現場で見覚えがある

データの構造はこうだった。

- 特徴量：100種類超。名前はすべてマスキング（`feature_001`形式）
- 目的変数：時系列で変化する連続値
- タスク：学習データの後に続く目的変数の予測（回帰）
- 評価指標：RMSE（小さいほどよい）
- リーダーボード：過去の研修受講生・講師陣を含む累計300件近い実績

目的変数を時系列でプロットしたとき、ぱっと見て分かった。**前半区間の標準偏差が後半の約2倍ある。** 何かが変わっている。

製造現場でいえば、これは見覚えのある構造だ。設備切替後の立ち上がり期間、定修明けの不安定期、原材料ロット切替直後の品質ばらつき——条件が変わった期間のデータは、安定期の予測に使うと精度を下げる。カラム名がマスキングされていても、時系列グラフが見せるパターンは現場で何度も見てきたものと重なった。

「これは前半が捨て期間で、後半が本物だ」——カラム名なしでもそう仮説が立った瞬間、半日でも勝負になると感じた。

## 5フェーズの壁打ちログ

セッション中、Claudeとの協働をCOMPETITION_LOG.mdというファイルにリアルタイムで記録しながら進めた。後から振り返ると、5つのフェーズに分かれていた。

```
| フェーズ | 主な実施者     | 内容                                          | 成果                       |
|---|---|---|---|
| 1        | Claude         | TimeSeriesSplit採用                           | 時系列順序保全             |
|          | 自分           | sample_weight 方針決定（Y分布の観察から）     | 後続改良の軸               |
| 2        | Claude         | 多手法並列比較                                | PLS 0.6378, RF 0.5938     |
| 3        | Claude + 自分  | 学習数 vs CV RMSE 可視化（Claude）→ 手法選定（自分） | RF n=31可視化 → LASSO採用 |
| 4        | Claude         | alpha範囲の探索                               | alpha=0.070821確定         |
| 5        | 自分 → Claude  | LASSO→PLS 2段階パイプライン 提案→実装         | CV RMSE 0.5355            |
```

### フェーズ1：時系列CVの採用と、後半重視の判断

最初のプロンプトはシンプルだった。

> 「TimeSeriesの構造を守りながら、複数の回帰モデルを比較して最適手法を探索してほしい。ハイパーパラメータも網羅的に最適化して」

ClaudeはTimeSeriesSplitを採用してきた。時系列構造を保全するための妥当な選択で、これはClaudeの知識から出てきた判断だ。

並行して自分は別のことをしていた。目的変数を時系列でプロットして、前半と後半の分布差を眺めていた。前半がばらつき、後半が落ち着いている。「これはsample_weightで後半を重視させるべきだ」——Y分布を観察した結果から出てきた、自分の判断だった。**この方針が、後続のすべての改良の軸になる。**

そして次にClaudeが提案してきた。

> 「特徴量エンジニアリングとして、時系列のlag特徴量を追加することを推奨します」

追加して試した。CV RMSEは改善しなかった。マスキングされた特徴量のどれが時系列的な意味を持つか、Claudeには分からない。「これは外れた」と判断して提案を捨てたのが午前11時ごろ。残り5時間半。**Claudeが外した1回目だった。**

### フェーズ2〜3：比較はClaude、選定は自分

ここからはClaudeに手法比較を回してもらった。PLS、ランダムフォレスト、ElasticNet、LASSOを並列で評価させ、結果が返ってきた。

```
PLS(n=3):  CV RMSE 0.6378
RF(tuned): CV RMSE 0.5938
ElasticNet / LASSO : 0.59台
```

数字だけ見ればRFが最良だ。ここで「どれを採用するか」を自分が決めた。

リーダーボードを眺めていて、ある傾向を感じた。CV精度が極端に高いモデルが、本番では崩れている形跡がある。300件近い提出履歴の分布を見ると、上位は派手なモデルではなく、地味に絞り込んだ系が並んでいた。明文化された根拠ではない、**リーダーボードの空気から感じた傾向だ**。

意味の分からない特徴量が100種類ある状況で、RFのような複雑なモデルは過学習の余地が大きすぎる。「ノイズに強く、自動で変数を絞れるLASSOで行く」——リーダーボードから感じた傾向と、直感を合わせた自分の判断だった。Claudeは手法の特性を演繹的に説明してくれるが、「リーダーボードの空気を読む」ことはできない。

### フェーズ4：Claudeがalphaを詰める

LASSO採用の決定を受けて、Claudeにalpha探索を任せた。0.001〜1.0の範囲を網羅探索し、alpha=0.070821でCV RMSEが最小になると返してきた。この間、自分はコードを1行も書いていない。

### フェーズ5：自分が現場感覚から提案した

フェーズ5でこう思った。LASSOで残った変数をそのまま予測に使うより、PLSで一段圧縮した方がいいはずだ、と。PLSは現場の多変量解析でよく使っていた手法だった。

> 「LASSOで係数ゼロになった特徴量を除外した後、残った変数でPLS回帰する2段階はどうか」

> 「有効なアプローチです。LASSOが特徴量選択器として機能し、PLSが残った変数間の共線性を吸収します。実装します」

この返答からコード生成まで数分だった。

```python
from sklearn.linear_model import Lasso
from sklearn.cross_decomposition import PLSRegression
import numpy as np

# 指数重みづけ（後述、自分の判断）
n = len(X_train_w)
sample_weights = np.exp(np.linspace(0, 1, n))

# フェーズ1: LASSOで特徴量選択
lasso = Lasso(alpha=0.070821)
lasso.fit(X_train_w, y_train, sample_weight=sample_weights)
selected = X_train_w.columns[lasso.coef_ != 0]

# フェーズ2: 残った特徴量でPLS
pls = PLSRegression(n_components=3)
pls.fit(X_train_w[selected], y_train)
y_pred = pls.predict(X_test_w[selected])
```

CV RMSE 0.5355——順位的に1位圏内だった。

## Claudeが2回目に外した——アンサンブルの罠

CV RMSE 0.5355が出た時点で、残り2時間を切っていた。Claudeに次の手を聞いた。

> 「さらに精度を上げるにはStackingまたはBlendingが有効です」

実装して提出した。CV RMSEはさらに下がった。しかし本番スコアの表示を見て、息が止まった。**スコアは逆に0.02落ちていた。**

残り90分。一瞬、Claudeに原因分析させて続行するか迷った。

> 「feature_321が訓練データ特有のノイズである可能性があります。アンサンブルによりそのノイズの影響が増幅された可能性があります」

冷静になれたのは、製造現場で「CVでは精度が出ているのに本番では外れる」パターンを何度も見てきた経験があったからだ。**これは過学習だ、戻れ**——そう判断してアンサンブル前の構成に戻した。

時間がなかったから戻れた。余裕があったらもう一手打って沼っていたかもしれない。**Claudeが外した2回目はこれだった。**

## 製造エンジニアの感覚が効いた3つの判断

### ① sample_weight の形状を「指数」にする

フェーズ1で「後半を重視する」と決めた方針を、どう実装するか。これが地味だが効いた。

最初は線形で試した（先頭0.5 → 末尾1.5の直線）。悪くはなかったが、本命の最後尾にもう少し強く重みをかけたい。指数に変えたところ、CV RMSEが安定した。

```python
sample_weights = np.exp(np.linspace(0, 1, n))  # 先頭→末尾で指数増加
```

製造現場でいえば、直近の安定稼働データを予測の重心に置く感覚と同じだ。設備の状態は時間で変わる。古いデータと新しいデータを同等に扱うより、直近に重みをかけた方が予測精度が出る——現場で繰り返してきた発想が、ここでも形を変えて働いた。

```python
sample_weights = np.exp(np.linspace(0, 1, n))  # 先頭→末尾で指数増加
```

### ② Time系特徴量の除外

「前半と後半で分布が違うなら、Time系の特徴量が訓練期間特有のノイズになっているはずだ」——グラフを見ながらそう仮説が立った。feature_321を含むTime系特徴量を学習から外した。

これはClaudeが提案したわけではない。製造現場で「定修明けや設備切替直後の期間のデータを解析から外す」という判断を繰り返してきた感覚が、変数名がマスキングされたデータの上で同じように働いた。

### ③ IQRからwinsorizeへの切り替え

外れ値処理は最初IQR法で書いた。Claudeとの壁打ちで「winsorizeは外れ値をゼロにせず境界値に揃えるため情報損失が少ない」と教わり、切り替えた。

```python
from scipy.stats.mstats import winsorize
X_train_w = X_train.apply(lambda col: winsorize(col, limits=[0.05, 0.05]))
```

これはClaudeが提案し、自分が採用した。知識の補完という意味では、最も素直なAI活用だった。

| 領域 | Claude | 自分 |

| 手法の並列比較・数値計算 | 高速・網羅的 | — |
| 手法の選定（何を採用するか） | 候補と特性を提示 | **最終判断** |

Claudeは2回、方向を外した。最初のlag特徴量提案と、後半のアンサンブル提案だ。どちらも「このデータが何を表しているか」という文脈をClaudeが持てないことから来ていた。

自分が判断したのは3つ——重みづけ、Time系除外、外れ値処理——だけ。それ以外のコードはClaudeが書いた。にもかかわらず結果を分けたのは、その3つだった。

## 製造業エンジニアへ——明日から試せる3ステップ

あなたの現場のデータには、カラム名がある。温度・圧力・タクトタイム・設備番号・ロット番号——それが何を意味するかを知っているのは現場のエンジニアだけだ。「この時期のデータは入れてはいけない」「この設備のデータは特殊だ」という判断は、カラム名には書いていない。

今回のアプローチを現場データで試すなら、こうなる。

1. **時系列グラフを必ずプロットする**：目的変数を時系列で並べ、「分布が変わる区間」を目で探す。それが見えたら、そこに `sample_weight` を入れる
2. **TimeSeriesSplit でCVを切る**：製造データは時系列構造を持つことが多い。ランダムCVは未来情報を漏らすので使わない
3. **LASSO で特徴量を絞る**：センサーが多いほど「効いていない変数」が多い。LASSOは自動で削ってくれる

コードはClaudeに書かせればいい。あなたが持っているのは、その「区間の意味」を読む力だ。

文脈を読む力は、現場にいたエンジニアが持つ本物の武器だ。コードが書けないことは弱点ではない——むしろ、コードを書く時間をAIに渡せる分、判断に集中できる側に立っている。
