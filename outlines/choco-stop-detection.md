## 構成

### 1. 現場あるある（共感）

- チョコ停は「ちょっと止まっただけ」と流されがちで、記録に残りにくい
- 積み重なると数十分・数時間のロスになるが、日次の生産日報には出てこない
- 「どこで止まっているのか」を問われても、感覚で「たぶんプレスが多い」としか言えない
- PLC のログは DB に入っているのに、誰も開いていない——この状況の共感を引く

---

### 2. 課題の深掘り

- **渋滞の連鎖という落とし穴**
  - 連続ラインでは、1か所で止まると後続ワークが詰まって下流設備も遅れて見える
  - 単純に「タクト遅れを集計」すると、渋滞を受けただけの下流設備が悪者に見える
  - 「プレスが遅い」は事実だが、「プレスが止めた」とは限らない
- **ログの構造**
  - PLC → DB に格納されるログのイメージを提示（wide format の表）
  - `work_id` × `設備_in_time` のカラム構成であることを確認する

```
work_id | furnace_in_time     | press_in_time       | polish_in_time      | ...
W-015   | 2024-03-15 08:07:00 | 2024-03-15 08:17:30 | 2024-03-15 08:24:00 | ...
W-016   | 2024-03-15 08:07:30 | 2024-03-15 08:18:30 | 2024-03-15 08:25:30 | ...
```

---

### 3. アイデアの核心

- **タクト＝前ワークとの間隔** で見る
  ```
  各設備のタクト = 自分が入った時刻 − 前のワークが入った時刻
  ```
- **先頭ワーク判定のロジック**
  ```
  タクトが閾値（標準タクト × 1.5 倍）を超えた
    かつ
  直前のワークは正常タクトだった
    →「先頭（原因ワーク）」= その設備に帰属
  
  直前のワークもすでに遅れていた
    →「後続（渋滞の波及）」= 除外
  
  同じ work_id が上流設備で先頭判定済み
    →「下流への波」= 除外
  ```
- フロー図（テキストで記述）
  ```
  [タクト計算] → [閾値超え?] → YES → [前ワークも遅れ?] → YES → 後続扱い（スキップ）
                                                         → NO  → 先頭ワーク（帰属）
                            → NO  → 正常
  ```

---

### 4. 実装

コードは3つのブロックで構成する。

#### ブロック1：データ読み込み

- DB から取得した CSV を読み込み、タイムスタンプ列を `datetime` 型に変換
- `.diff()` で設備ごとのタクトを一括計算

```python
df = pd.read_csv('choco_stop_log.csv')
for m in MACHINES:
    df[f'{m}_in_time'] = pd.to_datetime(df[f'{m}_in_time'])

for m in MACHINES:
    df[f'{m}_tact'] = df[f'{m}_in_time'].diff().dt.total_seconds()
```

#### ブロック2：先頭ワーク判定

- 標準タクトをログの中央値で自動推定
- ベクトル演算（`.shift()`）で前ワークの状態を比較し、先頭を判定
- 先頭から連続するタクト遅れを集計して「停止時間」を推定
- 上流設備で先頭判定済みの `work_id` は除外して根本原因設備に帰属

```python
is_slow   = df[tact_col] > standard_tact * TACT_THRESHOLD
is_leader = is_slow & ~is_slow.shift(1, fill_value=False)
```

#### ブロック3：可視化

- **ガントチャート**：横軸＝経過時間、縦軸＝設備。全ワークの通過リズムを細いバーで示し、チョコ停（先頭ワーク）を太い色付きバーで強調。先頭ワーク ID をラベル表示
- **棒グラフ**：設備ごとのチョコ停回数（左軸）と停止時間合計・分（右軸）を並列表示

- サンプルデータは `generate_samples.py` でリポジトリに同梱 → 手元で動かせる

---

### 5. 現場に適用するときのポイント

| ポイント | 内容 |
|---|---|
| 標準タクトの推定方法 | ログの中央値を使う。平均は外れ値（チョコ停）に引っ張られるため不向き |
| 閾値（何倍か）の決め方 | まず 1.5 倍で試し、誤検出が多ければ 2.0 倍に上げる。現場の「明らかに止まった」感覚と照らし合わせて調整する |
| DB 接続への差し替え | `pd.read_csv` を `pd.read_sql` に変えるだけ。その他のコードは変更不要 |
| ログの粒度 | 設備入口のセンサー信号をトリガーにした記録が理想。工程完了信号でも代用可 |

---

### 6. 実装上の課題と対応アイデア

- **課題1：複数設備が同時にチョコ停した場合**
  - まず試すこと：どちらの設備の遅れが先に発生したかをタイムスタンプで比較する
  - それでもダメなら：両方を先頭として記録し、現場担当者に確認を促すフラグを立てる
- **課題2：データ欠損（ワークが設備を通過しなかった記録がある）**
  - まず試すこと：欠損行を除外してからタクト計算する（`.dropna()` で対応）
  - 根本対策：欠損そのものを「設備停止」と捉え、別途イベントとして記録する仕組みを設ける
- **課題3：設備によって標準タクトが大きく異なる**
  - 設備ごとに閾値を個別設定できるよう、辞書でパラメータを管理する

---

### 7. まとめ

| 処理 | 使う技術 |
|---|---|
| タクト計算 | `pandas` `.diff()` |
| 先頭判定 | `.shift()` による前行比較 |
| 停止時間推定 | 先頭から連続するタクト遅れの積算 |
| 上流帰属フィルタ | `work_id` の重複チェック |
| 可視化 | `matplotlib` ガントチャート＋棒グラフ |

- **記事の締め一文**：「チョコ停の原因設備を正しく特定するには、『タクトが遅かった設備』ではなく『最初に止まった設備』を見つける必要がある。その判定を pandas の `.diff()` と `.shift()` だけで実装できる——というのが、この記事で伝えたかったことだ。」
